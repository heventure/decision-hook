# 实验与 GitHub 发布计划

## 实验一 · 插件和协议能否可靠接入

用无密钥 fixture 模拟正常返回、超时、连接失败、HTTP 429/500、无效 JSON、缺少答案、未知标签及低置信度。覆盖无关工具、成功测试、已明确的失败、取消和并行调用。核对是否只在目标用例发请求，失败时是否保留原退出状态和输出，日志是否只留下声明过的字段。再用真实 Pi 和 LM Studio 跑通断言失败、环境异常和停服三条流程，并明确记录 Pi 与 LM Studio 版本。

## 实验二 · 决策模型能否改善分诊

起步准备 30–50 条可脱敏的真实 Vitest 输出，另做合成边界例。记录来源、预先确定的标签和证据，并将真实与合成结果分别统计。按来源或故障家族切分调试集与留出集，避免同一故障的改写版本跨集合。为正常运行、非 Vitest 命令和格式异常单留一个触发验证集。样本可公开发布时附许可或来源，无法公开时提供独立的可复现替代样例。

用相同失败样本和同一分类标准比较仅规则、规则加普通 LLM 的结构化分类，以及规则加决策模型。统一输入、类别、超时和采样次数，记录具体模型、量化、宿主版本和运行设置。报告混淆矩阵、宏平均 F1、覆盖率、错误分诊和回退率。覆盖率是给出可用分类的比例，另报已给出分类中的准确率，避免把所有输入都回退得到虚高准确率。延迟报告包含成功和回退路径，并区分冷启动和已预热运行。

## 实验三 · 全流程是否更好

用同一套可重跑的失败仓库，对比 Pi 原流程及各实验方案。锁定宿主主模型和任务，冻结配置并随机交替运行。记录从测试失败到给出可执行下一步的时间、主模型请求次数、输入和输出 token、调用成本（能取到时）、错误建议和是否正确进入下一步。报告样本量、重复次数和代表性反例。主模型依然调用但输入 token 减少，就按测得的指标报告。仅当路线真的减少主模型调用时，才发布这项收益。

在看留出集结果前冻结发布判断。至少验证降级流程，并证明相对仅规则确有覆盖或质量收益，以及相对普通 LLM 路线至少有一项有用的实际收益。根据首轮基线确定可接受的错误分诊和额外等待时间，写明阈值的理由。小样本版本报告具体分子分母和限制。

## GitHub 展示与发行

1. 仓库首页展示一个失败样例的前后结果、安装条件和对比表。实际运行后填入已核验的结果，并链接到该次评测的固定提交、样本、配置、运行命令和汇总报告。原始完整日志只在可公开且经脱敏时上传。CI 跑不依赖密钥的契约用例；真实模型对照作为手工或可选工作流。
2. 在发布前定下正式包名、许可证、宿主版本范围、安装与卸载说明。检查包内容，使用干净 Pi 配置验证固定版本安装、启用、触发、断连、卸载。先用 Git 分发测试版，再考虑 npm 和 pi-package 关键字。首版由用户自行获取和配置模型。[Pi 包规范](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md)
3. 当前机器的 gh 已通过 GitHub API 只读验证。准备好的本地文档可通过 Git 发布到目标仓库。若要在 DSH 会话中调用 GitHub MCP，先在连接器市场添加 GitHub 连接，按需要配置只授权该仓库的细粒度 PAT，并验证连接和仓库访问。Codex CLI 中未见独立 GitHub MCP 服务；Codex 应用内的插件或账号连接配置不等同于该 CLI 的 MCP 列表。GitHub 凭据只用于开发和发布流程，插件运行不依赖它。[GitHub MCP](https://github.com/github/github-mcp-server) · [GitHub CLI](https://cli.github.com/manual/gh)
